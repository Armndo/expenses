# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

React 19 + Vite SPA (plain JS/JSX, no TypeScript) for the personal expense tracker. UI is MUI 7, data fetching is axios, routing is react-router-dom 7, charts are recharts. The backend is the sibling `api/` repo (see `../CLAUDE.md` for the multirepo picture).

## Commands

- **Dev server**: `npm run dev` (`npm run host` exposes it on the LAN)
- **Lint**: `npm run lint` (ESLint 9 flat config)
- **Build / preview**: `npm run build`, `npm run preview` (output in `dist/`)
- **Deploy**: `npm run deploy` (or `npm run deploy -- sta`) runs `scripts/deploy.sh`: asks for the environment (`dev`, `sta`, `pro`) and reads its settings from `.env`: `SSH_HOST`, `SSH_USER`, `SSH_BUILD`, and two templates, `SSH_DIR` (e.g. `/var/www/expenses.armn.do/{env}/client`) and `API_URL` (e.g. `https://expenses-api{.env}.armn.do`), where `{env}` becomes `dev`/`sta`/`pro` and `{.env}` becomes `.dev`/`.sta`/nothing in production. A prefix overrides any of them for one environment (`STA_SSH_DIR`, `PRO_API_URL`, `DEV_SSH_HOST`); a `SSH_DIR` or `API_URL` with no mark is refused so an environment never gets another one's value. `VITE_API_URL` stays for `npm run dev` only. It shows the resolved settings, asks for confirmation (production asks to type `pro`), builds locally with that `API_URL` (the server cannot build), zips `dist/`, then wipes the remote dir over SSH and uploads the new build. It refuses `/` or `~` as the remote dir. `DRY_RUN=1` only prints the commands. It is destructive on the remote; don't run it unasked.
- There is no test runner configured.

`app.yaml` is a leftover App Engine static-hosting config (nodejs20, SPA fallback to `dist/index.html`).

## Architecture

Routes are defined in `src/App.jsx`: `""` → `MainView`, `login` → `LoginView`, `*` → `NotFoundView`. `@/` aliases `src/` (via `jsconfig.json` + `vite-tsconfig-paths`); folders expose their members through an `index.js` barrel (`@/views`, `@/components`, `@/utils/functions`).

- **No global state or shared API client.** `MainView` owns one big `state` object and passes it down; each component that mutates data calls axios itself with `${api_url}` and `Authorization: Bearer ${localStorage.getItem("token")}`, and on failure removes the token. Preserve that pattern or refactor deliberately.
- `MainView` fetches `GET /data?date=...` and fills `state.sources` / `state.categories`. After create/update/delete, components re-fetch rather than patch local state.
- `ExpensesTable` + `ExpenseItem` render a grid with one column per source; rows go `source.expenses`, then `source.instalments` (lilac), then transfers (amber, `td.transfer`) and finally incomes (green, `td.income`): the period's charges are read first and the money moved after them, which keeps a payment of an earlier statement (`Paid`) apart from this period's expenses; the `Paid` chip in the header keeps payments visible without scrolling, and the income total is already in its chip. Incomes and transfers have no category, so their description spans the category column too (a transfer's shows only an arrow, `→` when it leaves the source and `←` when it arrives, and its description, without the other account; its amount is `signed_amount`). `ExpensesTable` computes the height of each group (`rows`) and `ExpenseItem` maps a row index to a group and a position, so the lists must stay in that order and shape. `visibleSources` (`@/utils/functions`) picks the sources shown: any with incomes, transfers, expenses or instalments (`transfers` may be missing if the API is older). The source header chips (`SourceChips` in `ExpensesTable.jsx`: Income, In full, Instalments, Total and the one below) are left out when their value is 0 to the cent, and the dots go only between the visible ones. They stay on one line (`.source-chips`, so the column grows to fit them, which matters in simple mode) except on a phone (portrait, up to 600px), where each source takes the whole width and they wrap centred with a gap instead of the dots (`.chip-dot` is hidden). On a phone the seven action buttons (`.main-actions`) are a grid of four equal columns with smaller text (they do not fit in one line), so switching between `simple` and `advanced` does not reflow them; the window cannot be made narrower than 500px, so check 412px in an iframe of that width. Next to each source name goes a `Credit` (cutoff set, `kind` card; soft purple `#e1bee7`) or `Debit` chip (soft brown `#d7ccc8`; `kindLabel` in `@/utils/functions`), and the source dropdowns of the expense, income and transfer forms show `Name (Credit)` or `Name (Debit)` (`sourceOptionLabel`). A card with no debt from earlier periods (`lastMonthPaid` in `@/utils/functions`: its `previous_balance` plus this month's transfers leaves nothing owed, or it has no previous balance because it is in the balance start month; only cards, only months with a balance) gets a light acid-green `Last month paid` chip (`#c5e1a5`, with what it owed at the close of the previous month when it was in debt, `Last month paid $4,200.00`: `lastMonthCleared`) next to its name, and a card that still carries debt gets a light red chip (`#ef9a9a`) that says how much it still owes, `Last month owed $1,234.56` (`lastMonthOwed`: what it owed at the close of the previous month less this month's payments, never below 0, in the card's currency); `lastMonthPaid` returns `null` (no chip) for accounts, months before the balance start and an API without `previous_balance`. Cards also get a `Paid` chip (the payments received this month, the same amber as the transfer rows) before `Owed`. The last chip comes from the API's `source.balance`: `Owed` (pink) for a card (`kind === "card"`, cutoff set) and `Balance` (blue, like the Balance chip of the month summary) for an account.
- `ExpensesModal` is the create/edit form (fields include `next` "Billed next period?" and `instalments`, which must be empty or an integer ≥ 2).
- `IncomesModal` is the create/edit form for incomes (source, date, amount ≠ 0, description and a `Skip budget` checkbox, `skip_budget`, off by default, with the hint "Salary, opening balance, loan repayment, etc.": an income that is not flagged gives back to the budget of its month; the source list has debit accounts only, `incomeSources`, and an existing income keeps its current source in the list even if it is a card), opened by the Income button or a green row's ✎; `MainView` keeps `incomeModal`/`income` in state and `openIncomeModal`. Delete is the row's ⌫. They call `POST|PUT|DELETE /incomes`. "Spent" stays expenses only. The subheader is up to five chips with just the amount, in this order: Spent (grey, like a source's Total), Debit (green, like the incomes; it is the API's `cash`, what the debit accounts hold), Debt (pink, like Owed), Last month owed (light red `#ef9a9a`, the API's `last_month_owed`: what the cards still owe from earlier periods) and Last month paid (acid green `#c5e1a5`, `last_month_paid`: what the cards that are paid owed at the close of the previous month), each left out when it is 0, Pending instalments (lilac `#bdbaff`, like the Instalments chip of a source; what the instalments already started will still bill, left out when it is 0) and Balance (blue; it is `cash - debt - pending_instalments`, so an instalment purchase weighs whole from its first month). The name is in the tooltip. They come straight from `summary` in the `GET /data` response (`state.summary`; a null value, i.e. before the balance start month or with a missing exchange rate, leaves that chip out instead of showing a dash), so the client does no money math for them. On a phone the summary chips are tighter (`.summary-chips` in `MainView.css`) so the totals and the rate fit one line (they wrap at 412px with the Pending instalments chip showing). Logout sits right of the next-month arrow in the header (an icon on a phone, text from 600px up), not in the button row; the arrows and Logout are all 30px high. The source chips are regular weight (`fontWeight: 400`), because the table head cell would make them bold.
- `TransfersModal` is the create/edit form for transfers between two sources (from, to, date, amount > 0, description), opened by the Transfer button or a blue row's ✎; `MainView` keeps `transferModal`/`transfer` in state and `openTransferModal`. Delete is the row's ⌫. They call `POST|PUT|DELETE /transfers`. A card payment is a transfer from an account to the card; it never changes the balance. `From` starts on the last origin chosen (`localStorage["lastTransferFrom"]`, `defaultTransferFrom`, only if it is still a debit account) and lists only debit accounts (`kind !== "card"`; an existing transfer keeps its current origin in the list even if it is a card) and `To` lists every source; each list leaves out the source chosen in the other one, so the origin and the destination can never be the same.
- The month is chosen from the card header: `‹ September 2026 ▾ ›`. The arrows call `changeDate` (one month back or forward) and the month button opens `MonthPicker` (`src/components/MonthPicker`): a popover with the year arrows and a 3x4 grid of months, like the Android app's, where months after the one following the current month are disabled. `selectMonth` in `MainView` saves the date in `localStorage["date"]` (day 2, as `changeDate` does) and calls `load`.
- Currencies (phase 1.9): a source's `currency` is `MXN` or `USD`. Its amounts show with `currencySymbol` (`$` or `US$`, `@/utils/functions`), and its Total and Balance chips add `≈ $x` in pesos with `state.rates` (from `/data`). The exchange rate is a chip in the subheader row (light indigo, just the amount with 2 to 3 decimals, `$18.399`, with the currency in its tooltip; a red `?` while it is missing, in which case the API sends `null` for Debit, Debt and Balance) that opens `RatesModal` (`PUT /rates/{currency}`). `TransfersModal` asks for "Received" when the two sources have different currencies, with the implied rate as help text, and sends it empty otherwise. A source's currency is set in `ManageModal`.
- Environment marker (phase 2.1): `env_name` (`@/env`) comes from the API URL (`.dev.` → `DEVELOP`, `.sta.` → `STAGING`, localhost → `LOCAL`, anything else, production, → empty), so it is right in a deployed build and in `npm run dev` alike. Outside production `App.jsx` tints the theme light red (`background.default` `#ffb4b8` on the body (not `#ffcdd2`, the tone of the Debt chip, which would vanish on it), `paper` `#ffebee` for the cards), titles the tab `Expenses · DEVELOP` and `MainView` shows a dark red chip with the name after the month arrows. In production nothing changes.
- `MonthPicker`'s button keeps one width in every month: the longest names (`LONGEST`) are rendered hidden in the same grid cell as the real one, so the arrows beside it never move.
- Overview (phase 2.2): `OverviewModal` has two tabs, as buttons that work like the app's chips (`ToggleButton`: contained when on, outlined when off, both options of a pair always visible; blue for the tabs, green for the toggles). `Categories` is what the app has: a second row of four buttons `By Amount`, `By Expenses`, `Bars` and `Pie` (`state.byAmount` and `state.overviewPie`, both in `localStorage`); `overviewBars` and `overviewSlices` (`@/utils/functions/overview.js`, the mirror of `domain/Overview.kt`) feed them: the bars are rows like the app's (emoji and name on one line, truncated, the bar, and its short value at the end; the axis is on top) so that thirty categories stay legible, they scroll inside the zone, and a negative category (refunds) is drawn with its absolute value, a red outline, a red value and a red value in its tooltip; the pie only has positive values, keeps its size and only its legend (colour, name, value and percentage) scrolls: under the pie on a phone and beside it from `sm` up. The tooltip of a bar or slice always shows the number of expenses and the total spent as money, in both views (it used to repeat the count in `By Expenses`). The size of the modal is set by the tab, not by what it holds, so it does not jump when the view or the data changes (`CATEGORIES_SIZE` and `EVOLUTION_SIZE` in `OverviewModal.jsx`): `Categories` has one width and one height for bars, pie and the empty message (the pie legend scrolls inside), `Evolution` has its own, wider, and on a phone it is a column where the header and `Close` stay in view and only the content scrolls. Never give the modal a width in `MainView.css`. `Evolution` asks `GET /history` when it opens and `evolutionCharts` builds three line charts, laid out by the width of the window (`EVOLUTION_GRID`): from 720px, two columns with `Spent` across both of the first row and `Balance and Debit` and `Instalments and Budget` side by side in the next one (so it fits in a desktop without scrolling); one column on a phone with compact axes (`compactMoney`) and a legend with the last value under each: `Spent` (every month), `Balance and Debit` (from the first month with a balance) and `Instalments and Budget` (from the first month with either; the budget line starts when it appears); a series with no value and a chart with no series are left out, and a `null` leaves a gap. Colours and behaviour: see the next bullet.
- Evolution (phases 2.3 to 2.5), in `OverviewModal.jsx` and `@/utils/functions/overview.js` (mirrored by the app's `domain/Evolution.kt`): a second row of buttons `Up to month | All` and `Linear | Log` (`localStorage`: `overviewTab`, `evolutionAll`, `evolutionLog`; the tab is remembered too). `Up to month` ends the charts at the month on the screen (`state.date`) and pads with `null` months after the history; `All` shows the whole range of `GET /history`, which now reaches the month of the last bill, so the months after the current one are a **projection** (registered instalments and `next` expenses, and the budget at the recent pace `budget_pace`): drawn with a dotted line and hollow dots (white centre; real months are filled dots, the current month counts as real), each real/projected line is split in `key` and `key_projected` (and the real value of every month travels in `key_value`). `Spent` is **bars** in both scales (`Bar` with `Cell`: filled when real, light fill and dotted outline when projected); the rest are straight lines (`type="linear"`). Line colours are the hue of the chip, darker (`EVOLUTION_COLORS`; the chips themselves use `CHIP_COLORS`, defined once in `overview.js`): Spent `#757575`, Debit `#43a047`, Balance `#1e88e5`, Instalments `#6a62e8`, Budget `#2e7d32`; a negative month (a refund) and the segments touching it are green, red for the budget (`BUDGET_COLORS`), through a gradient along the line (`negativeGradient`). The Y axis comes from `chartAxis(min, max, log)`: it stops at the data (the chart library would round it out to -$35k for a lowest value of -$3.9k) and goes to the next mark only when it is within 15% of the span. `Log` (not for `Balance and Debit`) is a two-piece scale, linear up to `LOG_FROM` ($1,000, negatives included) and logarithmic above it (`logScale`/`unlogScale`; the lines are drawn at the position of their value on a linear axis, and a negative value is drawn as its absolute value, in the colour of the case). Hovering a chart marks the same month in the three (`hovered` state of `Evolution`, a `ReferenceLine`) and each legend shows the values of that month (a dash where the chart has none; `· projected` and `· refund` notes); the legends reserve two lines so the dialog does not jump.
- Month range (phase 2.4): `GET /data` sends `range { first, last }`; `MainView` keeps it in `state.range` and `monthBounds()` gives `MonthPicker` its `min` and `max` (months and year arrows outside are disabled) and disables the previous/next month arrows at the ends. Until the range is known, the old rule (up to the month after the current one) applies.
- Layout of the month card (`MainView.css`): `div.expenses-card` is a flex column whose `max-height` is `100dvh - 2rem` (its 1rem margin included; `100vh` is only the fallback, because on a phone `vh` is taller than what is visible). The header and the buttons keep their height, however many lines the chips take, and `.expenses-table-container` takes what is left and is the only thing that scrolls. Do not give the table a `max-height` worked out with rem guesses.
- Settings and budget (phase 2): the `Settings` button next to Overview opens `SettingsModal`, which loads `GET /settings` and saves `PUT /settings` with `balance_start` and `budget_start` (`type="month"` inputs, `YYYY-MM`; an empty budget start means the same as the balance start) and `monthly_budget` (empty means none). The budget chips come from `summary` (the API does the math; `null` without a budget or before the budget start, so there is no chip): `Budget` is `budget_left` (this month's budget plus what the previous months left over or owe, minus `spent`), just the amount, light green while there is some left and light red with a negative amount when it is exceeded; before it, an outlined `budget_carry` chip (green text for what was saved, red for debt, tooltip `Budget carried over from the previous months`) that is left out at 0. Saving reloads the page, like the exchange rate.
- Manage and Sources overview (phase 3): the `Manage` button (between Overview and Settings) opens `ManageModal` (`src/components/ManageModal`), with `Sources` and `Categories` tabs: list with `Edit` and `Disable/Enable` (never delete) and a form. Sources: name, `Debit`/`Credit` (locked when `has_movements`), cutoff 0 to 27 and currency; categories: name, alias, colour and order. It calls `POST|PUT /sources` and `POST|PUT /categories` (disabling is `disabled` in the `PUT`), asks `confirm()` before changing a cutoff or currency or disabling (a card with debt gets a warning), refuses to disable the last source or the last debit account, and reloads `/data` through `reload`. Disabled sources and categories stay in `/data` and in the table of months where they have movements, and their money still counts; the pickers hide them with `activeSources` and `activeCategories` (`@/utils/functions`, they keep the one already selected, like `incomeSources`). The Overview has a third tab `Sources` (`SourcesTab`, `SOURCES_SIZE`): a `By Source | By Type` toggle (`state.sourcesByType`, `localStorage`) and bars or pie either by source or by type of expense, `Credit`, `Debit` and `Instalments` (`overviewSources` in `overview.js`, `items` and `types`, in pesos with `state.rates`, a source with no rate is left out and noted).
- Navigation and ordering (phase 3.8, delivery 2): a `Today` button after the next-month arrow, only outside the current month (`goToday`, `selectMonth` of the current one). A `Sort` select in the view bar (`SORT_OPTIONS` in `@/utils/functions/sorting.js`, `localStorage["sort"]`): date, description, category or amount, in both directions, applied **inside each group** of the table (expenses, instalments, transfers, incomes), so the order by groups that `ExpensesTable` and `ExpenseItem` depend on does not change. `state.rawSources` is what the API sent and `state.sources` the same with the rows sorted (`sortSources`, in `load` and in `changeSort`); a row with no value for the key (an income has no category) goes last, ties keep the API order, an instalment sorts by its monthly share and a transfer by what it means for the source. The source dropdowns say the cutoff of a card, `Invex (cutoff 6)` (`sourceOptionLabel`), and the category of the expense form is an `Autocomplete` that filters by name or alias without accents (`filterCategories`, names that start with what is typed first). There is no test runner, so the pure functions were checked with a `node` script.
- View bar and filters of the month (phase 3.8, delivery 4): under the action buttons, `ViewBar` (`src/components/ViewBar`) has a live search, a `Filters` button (a badge counts the filters that are on) and the `Sort` select (it used to be in the month header), with `12 of 47 records · 3 of 8 sources` while something is filtered. The panel has the type chips (`Expenses`, `Instalments`, `Incomes`, `Transfers`, remembered in `localStorage["filterTypes"]`), categories (multiple; incomes and transfers have none, so choosing one leaves them out), `Min` and `Max` amount fields in pesos (`state.rates`; the limits of the month are the placeholders) that only compare expenses and instalments (the monthly share; a row with no rate stays), one `Dates` field for the range (`DateRangeField`: a small calendar of its own, the first day touched is the start and the second the end in either order, limited to the dates the month has, which can reach back months because of instalments, and opening on the latest one) and `Clear`. There is no slider: one big purchase stretched its range and made it imprecise. The text matches every word in the description, category (name or alias), source, the other account of a transfer and the amount, without case or accents. The pure functions are in `@/utils/functions/filters.js` (`filterSources`, `filterBounds`, `filterCounts`, `emptyFilters`...); `state.sources` stays whole because the forms need every source, and `visibleSources(state)` applies `state.filters` (a source with no matches is empty and so hidden; the answer is kept while nothing changes, since every row asks for it). The table says `Nothing matches the filters.` with a button to clear them. Everything but the types is cleared when the month changes (`filtersMonth`). The totals chips do not change: the API computes them, and the header of each source (its `Last month owed/paid` chip and its money chips) is built from the whole source, not from the rows that pass the filters, so hiding the transfers does not make a paid card look unpaid; the chips that add up rows (`Income`, `In full`, `Instalments`, `Total`, `Paid`) are dimmed to half opacity (`DIMMED`) only when the filters leave out part of what that chip adds up (hiding the transfers dims `Paid`, hiding the instalments dims `Instalments` and `Total`), so they are not read as what is shown (their tooltip says `Paid (hidden rows)`), and `Owed` or `Balance`, which come from the API, stay as they are. No test runner: the functions were checked with a `node` script.
- Preview of the balance and going to the month of the record (phase 3.8, delivery 3): under the amount of the expense, income and transfer forms
  `RecordPreview` (`src/components/RecordPreview`, with the pure functions of `@/utils/functions/balancePreview.js`) shows how the sources it touches change
  with the amount that is written, one line each and without repeating the source chosen above (`Balance $20,000.00 → $19,500.00, bills in November 2026`; with several sources, as in a transfer, their name goes first, `Azteca balance ...`; `owed` for a card, red when an account would go negative and green when a card
  is left at 0), with what a card still owes from earlier periods (`Last month owed $1,300.00 → $0.00`) and the month's budget (an expense subtracts,
  an income adds unless it is `skip_budget`, only when it falls in the month on screen). It uses what `GET /data` already has (`balance` and
  `previous_balance` as of the month on screen) and adds in the client: a transfer counts by the calendar month of its date and needs no API; an expense
  or an income needs the billing month from `GET /period` (asked 350 ms after the last change, answers remembered), closes the first line as `, bills in November 2026 to April 2027`; without network or `period` that part does not appear and the form works the same. A record changes the month on screen only if its period is
  that month or an earlier one (otherwise it says `Applies from ...`), an instalment adds its monthly share for each period up to the month on screen,
  and an edit subtracts what the record was (`state.expenseOriginal`, `incomeOriginal`, `transferOriginal`, kept by `openModal`, `openIncomeModal` and
  `openTransferModal`). A transfer to a card has a small right-aligned outlined button `PAY OWED $X` under the amount that fills the amount with `lastMonthOwed` (the received one between currencies).
  After saving, `rememberPeriod(res.data.period)` puts the month of the record on screen. No test runner: the functions were checked with a `node` script.
- Width of the forms: every modal with the class `expenses-modal` (expense, income, transfer, settings, exchange rate and manage) has the same width, `min(92vw, 560px)`, set once in `MainView.css` (`.expenses-modal > div`, `box-sizing: border-box`), so it is nearly the whole screen on a phone and does not depend on its content (the preview lines of the forms used to change it while typing); the height is the screen's (`max-height: calc(100dvh - 2rem)`) and what does not fit scrolls. Do not give a form a width of its own.
- Per-user UI preferences and last selections live in `localStorage`: `token`, `date`, `byAmount`, `simple`, `lastSource`, `lastIncomeSource` (the income form's own, since a card chosen in an expense is not an option there), `lastCategory`, `lastTransferFrom`.
- Instalment amounts are shown as `amount / instalments` rounded to cents (`monthlyShare` in `@/utils/functions`), the same rounding the API uses for sums and balances, so a card's chips add up to what the bank bills. It rounds on whole cents with halves away from zero, not with `Math.round(amount / n * 100) / 100`: floats turn an exact 1200.465 (14405.58 / 12) into 1200.4649999, which made the web show 1200.46 while the API billed 1200.47 and the difference grew by a cent every month of the instalment.

## Environment

`VITE_API_URL` in `.env` selects the API base URL (default `http://localhost:8000`). The API must list the client origin in its `FRONTEND_ORIGIN` for CORS.

## Conventions

- 2-space indentation, double quotes, no semicolons in components (`src/env.js` uses tabs; match the file you edit).
- Conventional commits enforced by Commitlint + Husky; Commitizen config in `.cz.toml`. Versions/changelog are bumped with commitizen.
- `.env`, `dist/` and `dist-*.zip` are git-ignored; never commit them.
