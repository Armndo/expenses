# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

React 19 + Vite SPA (plain JS/JSX, no TypeScript) for the personal expense tracker. UI is MUI 7, data fetching is axios, routing is react-router-dom 7, charts are recharts. The backend is the sibling `api/` repo (see `../CLAUDE.md` for the multirepo picture).

## Commands

- **Dev server**: `npm run dev` (`npm run host` exposes it on the LAN)
- **Lint**: `npm run lint` (ESLint 9 flat config)
- **Build / preview**: `npm run build`, `npm run preview` (output in `dist/`)
- **Deploy**: `npm run deploy` (or `npm run deploy -- sta`) runs `scripts/deploy.sh`: asks for the environment (`dev`, `sta`, `pro`) and reads its settings from `.env`: `SSH_HOST`, `SSH_USER`, `SSH_BUILD`, and two templates, `SSH_DIR` (e.g. `/var/www/expenses.armn.do/{env}/client`) and `API_URL` (e.g. `https://expenses-api{.env}.armn.do`), where `{env}` becomes `dev`/`sta`/`pro` and `{.env}` becomes `.dev`/`.sta`/nothing in production. A prefix overrides any of them for one environment (`STA_SSH_DIR`, `PRO_API_URL`, `DEV_SSH_HOST`); a `SSH_DIR` or `API_URL` with no mark is refused so an environment never gets another one's value. `VITE_API_URL` stays for `npm run dev` only. It shows the resolved settings, asks for confirmation (production asks to type `pro`), builds locally with that `API_URL` (the server cannot build), zips `dist/`, then wipes the remote dir over SSH and uploads the new build. It refuses `/` or `~` as the remote dir. `DRY_RUN=1` only prints the commands. It is destructive on the remote; don't run it unasked.
- There is no test runner configured.

`app.yaml` is a leftover App Engine static-hosting config (nodejs20, SPA fallback to `dist/index.html`).

## Architecture

Routes are defined in `src/App.jsx`: `""` → `MainView`, `login` → `LoginView`, `*` → `NotFoundView`. `@/` aliases `src/` (via `jsconfig.json` + `vite-tsconfig-paths`); folders expose their members through an `index.js` barrel (`@/views`, `@/components`, `@/utils/functions`).

- **No global state or shared API client.** `MainView` owns one big `state` object and passes it down; each component that mutates data calls axios itself with `${api_url}` and `Authorization: Bearer ${localStorage.getItem("token")}`, and on failure removes the token. Preserve that pattern or refactor deliberately.
- `MainView` fetches `GET /data?date=...` and fills `state.sources` / `state.categories`. After create/update/delete, components re-fetch rather than patch local state.
- `ExpensesTable` + `ExpenseItem` render a grid with one column per source; rows go `source.expenses`, then `source.instalments` (lilac), then transfers (amber, `td.transfer`) and finally incomes (green, `td.income`): the period's charges are read first and the money moved after them, which keeps a payment of an earlier statement (`Paid`) apart from this period's expenses; the `Paid` chip in the header keeps payments visible without scrolling, and the income total is already in its chip. Incomes and transfers have no category, so their description spans the category column too (a transfer's shows only an arrow, `→` when it leaves the source and `←` when it arrives, and its description, without the other account; its amount is `signed_amount`). `ExpensesTable` computes the height of each group (`rows`) and `ExpenseItem` maps a row index to a group and a position, so the lists must stay in that order and shape. `visibleSources` (`@/utils/functions`) picks the sources shown: any with incomes, transfers, expenses or instalments (`transfers` may be missing if the API is older). The source header chips (`SourceChips` in `ExpensesTable.jsx`: Income, In full, Instalments, Total and the one below) are left out when their value is 0 to the cent, and the dots go only between the visible ones. They stay on one line (`.source-chips`, so the column grows to fit them, which matters in simple mode) except on a phone (portrait, up to 600px), where each source takes the whole width and they wrap centred with a gap instead of the dots (`.chip-dot` is hidden). On a phone the action buttons (`.main-actions`) stay on one line with smaller text so switching between `simple` and `advanced` does not reflow them; the window cannot be made narrower than 500px, so check 412px in an iframe of that width. Next to each source name goes a `Credit` (cutoff set, `kind` card; soft purple `#e1bee7`) or `Debit` chip (soft brown `#d7ccc8`; `kindLabel` in `@/utils/functions`), and the source dropdowns of the expense, income and transfer forms show `Name (Credit)` or `Name (Debit)` (`sourceOptionLabel`). A card with no debt from earlier periods (`lastMonthPaid` in `@/utils/functions`: its `previous_balance` plus this month's transfers leaves nothing owed, or it has no previous balance because it is in the balance start month; only cards, only months with a balance) gets a light acid-green `Last month paid` chip (`#c5e1a5`) next to its name, and a card that still carries debt gets a light red `Last month not paid` chip (`#ef9a9a`); `lastMonthPaid` returns `null` (no chip) for accounts, months before the balance start and an API without `previous_balance`. Cards also get a `Paid` chip (the payments received this month, the same amber as the transfer rows) before `Owed`. The last chip comes from the API's `source.balance`: `Owed` (pink) for a card (`kind === "card"`, cutoff set) and `Balance` (blue, like the Balance chip of the month summary) for an account.
- `ExpensesModal` is the create/edit form (fields include `next` "Billed next period?" and `instalments`, which must be empty or an integer ≥ 2).
- `IncomesModal` is the create/edit form for incomes (source, date, amount ≠ 0, description; the source list has debit accounts only, `incomeSources`, and an existing income keeps its current source in the list even if it is a card), opened by the Income button or a green row's ✎; `MainView` keeps `incomeModal`/`income` in state and `openIncomeModal`. Delete is the row's ⌫. They call `POST|PUT|DELETE /incomes`. "Spent" stays expenses only. The subheader is up to five chips with just the amount, in this order: Spent (grey, like a source's Total), Debit (green, like the incomes; it is the API's `cash`, what the debit accounts hold), Debt (pink, like Owed), Pending instalments (lilac `#bdbaff`, like the Instalments chip of a source; what the instalments already started will still bill, left out when it is 0) and Balance (blue; it is `cash - debt - pending_instalments`, so an instalment purchase weighs whole from its first month). The name is in the tooltip. They come straight from `summary` in the `GET /data` response (`state.summary`; a null value, i.e. before the balance start month or with a missing exchange rate, leaves that chip out instead of showing a dash), so the client does no money math for them. On a phone the summary chips are tighter (`.summary-chips` in `MainView.css`) so the totals and the rate fit one line (they wrap at 412px with the Pending instalments chip showing). Logout sits right of the next-month arrow in the header (an icon on a phone, text from 600px up), not in the button row; the arrows and Logout are all 30px high. The source chips are regular weight (`fontWeight: 400`), because the table head cell would make them bold.
- `TransfersModal` is the create/edit form for transfers between two sources (from, to, date, amount > 0, description), opened by the Transfer button or a blue row's ✎; `MainView` keeps `transferModal`/`transfer` in state and `openTransferModal`. Delete is the row's ⌫. They call `POST|PUT|DELETE /transfers`. A card payment is a transfer from an account to the card; it never changes the balance. `From` starts on the last origin chosen (`localStorage["lastTransferFrom"]`, `defaultTransferFrom`, only if it is still a debit account) and lists only debit accounts (`kind !== "card"`; an existing transfer keeps its current origin in the list even if it is a card) and `To` lists every source; each list leaves out the source chosen in the other one, so the origin and the destination can never be the same.
- The month is chosen from the card header: `‹ September 2026 ▾ ›`. The arrows call `changeDate` (one month back or forward) and the month button opens `MonthPicker` (`src/components/MonthPicker`): a popover with the year arrows and a 3x4 grid of months, like the Android app's, where months after the one following the current month are disabled. `selectMonth` in `MainView` saves the date in `localStorage["date"]` (day 2, as `changeDate` does) and calls `load`.
- Currencies (phase 1.9): a source's `currency` is `MXN` or `USD`. Its amounts show with `currencySymbol` (`$` or `US$`, `@/utils/functions`), and its Total and Balance chips add `≈ $x` in pesos with `state.rates` (from `/data`). The exchange rate is a chip in the subheader row (light indigo, just the amount with 2 to 3 decimals, `$18.399`, with the currency in its tooltip; a red `?` while it is missing, in which case the API sends `null` for Debit, Debt and Balance) that opens `RatesModal` (`PUT /rates/{currency}`). `TransfersModal` asks for "Received" when the two sources have different currencies, with the implied rate as help text, and sends it empty otherwise. There is no screen to set a source's currency: use `PUT /sources/{id}`.
- Environment marker (phase 2.1): `env_name` (`@/env`) comes from the API URL (`.dev.` → `DEVELOP`, `.sta.` → `STAGING`, localhost → `LOCAL`, anything else, production, → empty), so it is right in a deployed build and in `npm run dev` alike. Outside production `App.jsx` tints the theme light red (`background.default` `#ffb4b8` on the body (not `#ffcdd2`, the tone of the Debt chip, which would vanish on it), `paper` `#ffebee` for the cards), titles the tab `Expenses · DEVELOP` and `MainView` shows a dark red chip with the name after the month arrows. In production nothing changes.
- `MonthPicker`'s button keeps one width in every month: the longest names (`LONGEST`) are rendered hidden in the same grid cell as the real one, so the arrows beside it never move.
- Overview (phase 2.2): `OverviewModal` has two tabs, as buttons that work like the app's chips (`ToggleButton`: contained when on, outlined when off, both options of a pair always visible; blue for the tabs, green for the toggles). `Categories` is what the app has: a second row of four buttons `By Amount`, `By Expenses`, `Bars` and `Pie` (`state.byAmount` and `state.overviewPie`, both in `localStorage`); `overviewBars` and `overviewSlices` (`@/utils/functions/overview.js`, the mirror of `domain/Overview.kt`) feed them: the bars are rows like the app's (emoji and name on one line, truncated, the bar, and its short value at the end; the axis is on top) so that thirty categories stay legible, they scroll inside the zone, and a negative category (refunds) is drawn with its absolute value, a red outline, a red value and a red value in its tooltip; the pie only has positive values, keeps its size and only its legend (colour, name, value and percentage) scrolls: under the pie on a phone and beside it from `sm` up. The tooltip of a bar or slice always shows the number of expenses and the total spent as money, in both views (it used to repeat the count in `By Expenses`). The size of the modal is set by the tab, not by what it holds, so it does not jump when the view or the data changes (`CATEGORIES_SIZE` and `EVOLUTION_SIZE` in `OverviewModal.jsx`): `Categories` has one width and one height for bars, pie and the empty message (the pie legend scrolls inside), `Evolution` has its own, wider, and on a phone it is a column where the header and `Close` stay in view and only the content scrolls. Never give the modal a width in `MainView.css`. `Evolution` asks `GET /history` when it opens and `evolutionCharts` builds three line charts, laid out by the width of the window (`EVOLUTION_GRID`): from 720px, two columns with `Spent` across both of the first row and `Balance and Debit` and `Instalments and Budget` side by side in the next one (so it fits in a desktop without scrolling); one column on a phone with compact axes (`compactMoney`) and a legend with the last value under each: `Spent` (every month), `Balance and Debit` (from the first month with a balance) and `Instalments and Budget` (from the first month with either; the budget line starts when it appears); a series with no value and a chart with no series are left out, and a `null` leaves a gap. Line colours are in `EVOLUTION_COLORS`: Balance `#1976d2`, Debit `#2e7d32`, Spent `#616161`, Instalments `#7e57c2`, Budget `#ef6c00`.
- Layout of the month card (`MainView.css`): `div.expenses-card` is a flex column whose `max-height` is `100dvh - 2rem` (its 1rem margin included; `100vh` is only the fallback, because on a phone `vh` is taller than what is visible). The header and the buttons keep their height, however many lines the chips take, and `.expenses-table-container` takes what is left and is the only thing that scrolls. Do not give the table a `max-height` worked out with rem guesses.
- Settings and budget (phase 2): the `Settings` button next to Overview opens `SettingsModal`, which loads `GET /settings` and saves `PUT /settings` with `balance_start` and `budget_start` (`type="month"` inputs, `YYYY-MM`; an empty budget start means the same as the balance start) and `monthly_budget` (empty means none). The budget chips come from `summary` (the API does the math; `null` without a budget or before the budget start, so there is no chip): `Budget` is `budget_left` (this month's budget plus what the previous months left over or owe, minus `spent`), just the amount, light green while there is some left and light red with a negative amount when it is exceeded; before it, an outlined `budget_carry` chip (green text for what was saved, red for debt, tooltip `Budget carried over from the previous months`) that is left out at 0. Saving reloads the page, like the exchange rate.
- Per-user UI preferences and last selections live in `localStorage`: `token`, `date`, `byAmount`, `simple`, `lastSource`, `lastCategory`, `lastTransferFrom`.
- Instalment amounts are shown as `amount / instalments` rounded to cents (`monthlyShare` in `@/utils/functions`), the same rounding the API uses for sums and balances, so a card's chips add up to what the bank bills. It rounds on whole cents with halves away from zero, not with `Math.round(amount / n * 100) / 100`: floats turn an exact 1200.465 (14405.58 / 12) into 1200.4649999, which made the web show 1200.46 while the API billed 1200.47 and the difference grew by a cent every month of the instalment.

## Environment

`VITE_API_URL` in `.env` selects the API base URL (default `http://localhost:8000`). The API must list the client origin in its `FRONTEND_ORIGIN` for CORS.

## Conventions

- 2-space indentation, double quotes, no semicolons in components (`src/env.js` uses tabs; match the file you edit).
- Conventional commits enforced by Commitlint + Husky; Commitizen config in `.cz.toml`. Versions/changelog are bumped with commitizen.
- `.env`, `dist/` and `dist-*.zip` are git-ignored; never commit them.
